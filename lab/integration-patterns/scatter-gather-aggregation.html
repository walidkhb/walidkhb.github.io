Scatter-Gather: Multi-Source Account Aggregation for SAMA Open Banking

Fanning out balance and transaction queries across a fragmented KSA bank estate — legacy CBS, digital core, card processor, investment accounts — and assembling a compliant Open Banking response under a 300ms wall-clock budget: timeout allocation, partial-result semantics, IBM ACE and Spring Boot wiring, and the caching layer that makes it survivable in production.

Overview

SAMA Open Banking Phase 2 requires participant banks to expose a consolidated account view to authorised Third-Party Providers (TPPs) — a customer’s current accounts, savings, credit cards, and investment portfolio surfaced through a single API response. For a large KSA bank that grew by acquisition, that data does not live in one system. It lives in a legacy core banking system (CICS-era Temenos or Misys), a digital banking platform, a card-processing platform, and possibly a separate investment and custody system. The integration layer that assembles the unified response is a scatter-gather aggregator.

Scatter-gather is one of the original Enterprise Integration Patterns: send one request outbound to N recipients in parallel, collect the N responses, and return a single composed response to the original caller. It is straightforward to describe and genuinely difficult to implement correctly in a financial services context because every trade-off has a regulatory or customer-experience consequence — most obviously the question of what to do when one of the N downstream calls fails or times out within the wall-clock budget.

SAMA Open Banking Phase 2 scope

Phase 2 of SAMA’s Open Banking Framework (launched in full during 2025) mandates that banks expose account information and transaction history APIs conforming to the SAMA Open Banking Technical Specification v2.0. The spec sets a maximum response time of 3,000ms for account listing and 5,000ms for transaction history at the API gateway level. The scatter-gather aggregation layer must complete within a margin of that budget — leaving room for the gateway overhead, TLS handshake, and serialisation. A practical internal target is 2,500ms wall-clock for the aggregation, 300ms for a single-system account query that the cache serves.

When to use it

The scatter-gather pattern earns its complexity cost in one specific situation: the response requires data from multiple independent sources that cannot be queried together, and those sources can be called in parallel to meet a latency budget that sequential calls would miss.

Pattern Use when Do not use when
Scatter-Gather N independent systems; partial result is acceptable; latency budget is tighter than sum of sequential calls Sources are dependent (B needs A’s result); all-or-nothing is required; N = 1
Sequential call chain Each call depends on the prior result; ordering matters for business logic Sources are independent; latency is critical; a slow source should not block others
API composition (BFF) Response needs data from two or three services; client-driven aggregation is acceptable Many sources (>4); a backend aggregation contract is required; the client is a TPP not in your control
Event-driven read model Query volume is high; freshness within seconds is acceptable; Debezium + Kafka pipeline is already in place Real-time freshness is required; data sources cannot produce events; regulatory audit trail per query is needed

For SAMA Open Banking, scatter-gather is the right choice when: the account universe spans multiple systems, the TPP requires a single consolidated response per SAMA spec, and the bank cannot afford the 2–4 second latency of sequential calls to its legacy core plus card platform plus digital core. When a pre-built read model fed by CDC is available (from a Debezium pipeline into a Redis or Elasticsearch projection), use that instead — it is simpler and faster. Scatter-gather is the fallback when the read model does not exist or cannot be built within the programme timeline.

Fan-out design

The fan-out side of scatter-gather requires three decisions before writing code: which systems are in scope, what the request schema looks like for each, and whether the fan-out is static (always call all N systems) or dynamic (derive the target list from the customer’s product holding at query time).

Dynamic fan-out is correct for a KSA bank: a customer with only current accounts and a credit card should not trigger a call to the investment platform. Dynamic fan-out reduces downstream load and reduces the chance that a slow or unavailable system delays a response for customers who have no products on that system. The product holding map — which systems hold products for which customers — must be maintained centrally, usually in a party and product registry that the integration layer queries at the start of each Open Banking session.

Timeout budget allocation

The 3,000ms SAMA Open Banking SLA is a wall-clock budget that must be allocated across every hop in the response path. Working backwards from the SLA:

  • TLS + gateway overhead: 50ms
  • Product registry lookup: 50ms (served from Redis; no network hop to CBS)
  • Scatter-gather wall-clock: 2,500ms (the entire parallel fan-out must complete within this)
  • Response assembly and serialisation: 150ms
  • Total: 2,750ms, leaving 250ms margin against the 3,000ms limit

The 2,500ms budget for the scatter-gather fan-out is the budget for the slowest downstream call that completes within the window. Fast calls (a modern digital core returning in 80ms) return early; slow calls (a legacy CICS CBS that consistently takes 1,800ms) define the wall clock. Any downstream that does not respond within 2,500ms must be treated as a timeout and handled as a partial result — which means the per-call timeout for each downstream must be set to 2,400ms (100ms less than the fan-out budget, to allow for thread scheduling overhead).

Do not give every downstream the same timeout

Setting a uniform 2,400ms timeout across all downstreams means a fast digital core that returns in 80ms still waits for the 2,400ms window before the caller considers it timed out if it fails. The right design is a per-downstream timeout derived from that system’s p99 latency plus a 50% safety margin, subject to the 2,400ms hard ceiling. A system with a p99 of 200ms gets a 300ms timeout. A legacy CBS with a p99 of 1,500ms gets a 2,250ms timeout. Configure these per-downstream, measure them in production, and tune quarterly.

IBM ACE implementation

IBM ACE 12 implements scatter-gather through its Fan-out and Fan-in message flow nodes, introduced as a production-ready pattern in ACE 12.0.6. The Fan-out node dispatches a copy of the incoming message to N parallel flows simultaneously; each flow processes its branch independently; the Fan-in node aggregates the results when either all branches complete or the fan-in timeout expires.

  1. Product registry lookup (Compute node)

    A Compute node or DatabaseRetrieve node queries the product registry for the consented customer. The result is a list of system codes (CBS, DIGITAL, CARD, INVEST) stored in a local environment variable. This list drives the dynamic fan-out in the next node.

  2. Fan-out node configuration

    Configure the Fan-out node with a distributor expression that iterates over the system-code list. Set the Fan-out mode to Parallel. Each branch receives a copy of the original request message plus the system code for that branch injected into the local environment tree.

  3. Per-branch adapter subflows

    Each branch routes via a RouteToLabel node to a system-specific subflow. The CBS subflow translates the request to a CICS COMMAREA format via DFDL and calls the mainframe through the CICS TCP/IP link; the digital core subflow calls a REST API; the card subflow calls a SOAP/XML gateway. Each subflow normalises its response to the canonical account schema before returning to the fan-in node.

  4. Per-branch timeout configuration

    Wrap each branch’s outbound call in an ACE Timeout Control flow with the per-system timeout value. When a timeout fires, the timeout flow propagates a structured error message to the fan-in node using the Failure terminal — not a Java exception. The fan-in node must be configured to accept failure messages as valid partial inputs.

  5. Fan-in aggregation

    Configure the Fan-in node to aggregate results as they arrive. Set the fan-in timeout to 2,400ms (the hard ceiling). Configure Allow partial completion to true — this is the flag that determines whether a timed-out or erroring branch causes the entire aggregation to fail or allows the available results to proceed. For Open Banking, partial is always the right choice.

  6. Response assembly (Compute node)

    A final Compute node iterates over the aggregated results, identifies which branches succeeded and which timed out or failed, and assembles the SAMA Open Banking JSON response. It appends a partialData flag and per-system status field when any branch did not return a full result — required by the SAMA spec for degraded responses.

AccountAggregator.esql — ACE fan-in result assemblyesql
CREATE COMPUTE MODULE AssembleAggregatedAccounts
  CREATE FUNCTION Main() RETURNS BOOLEAN
  BEGIN
    DECLARE partial   BOOLEAN  FALSE;
    DECLARE acctIndex INTEGER 1;
    DECLARE branch    REFERENCE TO InputRoot.XMLNSC.FanInOutput.Branch[1];

    WHILE LASTMOVE(branch) DO
      IF branch.status = 'SUCCESS' THEN
        -- Copy canonical account list from this branch into output
        DECLARE acct REFERENCE TO branch.CanonicalAccounts.Account[1];
        WHILE LASTMOVE(acct) DO
          SET OutputRoot.JSON.Data.accounts.Item[acctIndex] = acct;
          SET acctIndex = acctIndex + 1;
          MOVE acct NEXTSIBLING;
        END WHILE;
      ELSEIF branch.status = 'TIMEOUT'
          OR branch.status = 'ERROR' THEN
        SET partial = TRUE;
        -- Log the degraded system for the response metadata
        SET OutputRoot.JSON.Data.meta.degradedSystems[] = branch.systemCode;
      END IF;
      MOVE branch NEXTSIBLING;
    END WHILE;

    SET OutputRoot.JSON.Data.meta.partialData = partial;
    SET OutputRoot.JSON.Data.meta.queryTimestamp =
        CAST(CURRENT_TIMESTAMP AS CHARACTER FORMAT 'IU');

    PROPAGATE TO TERMINAL 'out1';
    RETURN FALSE;
  END;
END MODULE;

Spring Boot implementation

When the aggregation layer is not built on IBM ACE — common for greenfield Open Banking gateway implementations on OpenShift — Spring Boot 3 with CompletableFuture and VirtualThreads (Java 21) is the idiomatic choice. The CompletableFuture.allOf() and CompletableFuture.anyOf() methods handle fan-out/fan-in; Resilience4j decorates each downstream call with its own circuit breaker and timeout policy.

AccountAggregationService.java — virtual-thread scatter-gatherjava
@Service
public class AccountAggregationService {

    private final ProductRegistryClient registry;
    private final Map<SystemCode, AccountSourceAdapter> adapters;
    private final AggregationCache cache;

    public AggregatedAccountResponse aggregate(String consentId, String customerId) {
        var targets = registry.getProductSystems(customerId); // e.g. [CBS, DIGITAL, CARD]

        var futures = targets.stream()
            .map(system -> fetchWithTimeout(system, customerId, consentId))
            .toList();

        var all = CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]));

        try {
            all.get(2_400, TimeUnit.MILLISECONDS); // hard ceiling
        } catch (TimeoutException e) {
            all.cancel(false); // cancel remaining; collect completed below
        } catch (InterruptedException | ExecutionException ignored) {}

        return assembleResult(targets, futures);
    }

    private CompletableFuture<SystemResult> fetchWithTimeout(
            SystemCode system, String customerId, String consentId) {

        return CompletableFuture
            .supplyAsync(() -> adapters.get(system).fetchAccounts(customerId, consentId),
                Executors.newVirtualThreadPerTaskExecutor())
            .orTimeout(adapters.get(system).getTimeoutMs(), TimeUnit.MILLISECONDS)
            .handle((result, ex) -> ex == null
                ? new SystemResult(system, result, Status.SUCCESS)
                : new SystemResult(system, null,
                    ex instanceof TimeoutException ? Status.TIMEOUT : Status.ERROR));
    }

    private AggregatedAccountResponse assembleResult(
            List<SystemCode> targets,
            List<CompletableFuture<SystemResult>> futures) {

        var results = futures.stream()
            .map(f -> f.isDone() && !f.isCancelled() && !f.isCompletedExceptionally()
                ? f.join()
                : new SystemResult(null, null, Status.TIMEOUT))
            .toList();

        var accounts = results.stream()
            .filter(r -> r.status() == Status.SUCCESS)
            .flatMap(r -> r.accounts().stream())
            .toList();

        var degraded = results.stream()
            .filter(r -> r.status() != Status.SUCCESS)
            .map(r -> r.system().name())
            .toList();

        return new AggregatedAccountResponse(accounts, !degraded.isEmpty(), degraded);
    }
}
Virtual threads change the capacity model

Java 21 virtual threads (Project Loom) eliminate the thread-per-downstream scalability ceiling that made scatter-gather expensive on platform thread pools. Each downstream call runs on its own virtual thread; blocking I/O parks the virtual thread and yields the carrier thread for other work. At 100 concurrent Open Banking sessions each fanning out to 3 systems, you need 300 concurrent I/O calls — trivial for virtual threads, expensive for a fixed platform thread pool of 200. If you are building the aggregation layer on Java 17 or earlier, use a dedicated ForkJoinPool with a parallelism ceiling matched to your downstream concurrency limits.

Partial result handling

The partial result decision is the hardest business call in a scatter-gather implementation, and it must be made explicitly — not defaulted by the engineering team. The choices are:

  • Return available + flag degraded: The response includes accounts from the systems that responded successfully. A meta.partialData: true flag and a meta.degradedSystems array tell the TPP which systems did not respond. This is what the SAMA Open Banking spec permits during a declared degraded period.
  • Fail the entire request: If any mandatory system (e.g. the primary CBS) does not respond, return a 503 with a Retry-After header. Use this for systems that hold accounts the customer is likely querying specifically — not a justified default for the investment platform if only 20% of customers have investment accounts.
  • Serve from stale cache: If a fresh partial result is unacceptable but a stale complete result from a prior successful query is acceptable, serve the cache entry and flag its age. This requires a cache TTL policy and a consent-aware cache key (covered in the next section).
Never silently omit accounts

The worst partial-result behaviour is returning an account list that appears complete but is missing accounts from a timed-out system — without any flag to signal the omission. A TPP that shows a customer their “balance” from an incomplete response without indicating the data is partial creates a consumer harm risk and a potential SAMA compliance issue (the SAMA Open Banking spec explicitly requires banks to indicate when a response is incomplete). Always surface the partial flag; never return a 200 OK response with silently missing data.

Circuit breaker integration

Each downstream in the scatter-gather must be independently circuit-broken. If the legacy CBS is in an open circuit state, the fan-out should not even attempt to call it — it should immediately return a CIRCUIT_OPEN status for that branch and let the aggregation proceed without waiting for the CBS timeout to expire. This reduces response time for all CBS-circuit-open periods from 2,250ms (the CBS per-call timeout) to <5ms (the circuit breaker check).

Response caching

Open Banking account queries have a characteristic usage pattern: a customer opens their finance app, grants consent, and the TPP calls the account listing once per session startup, then periodically in the background. The same aggregated result is requested multiple times in a short window. Caching the assembled result — not individual downstream results — at a 60-second TTL is the highest-leverage performance optimisation available, reducing the fan-out call rate by 70–90% in a typical Open Banking session.

Cache key design for Open Banking must incorporate the consent ID, not just the customer ID. A single customer may have multiple active consents from different TPPs, each with a different account scope. The cache key must be consent:{consentId}:accounts. The TTL must be bounded by the consent expiry — a consent expiring in 30 seconds must not be served from a 60-second-old cache entry that pre-dates the expiry.

Partial results should be cached with a flag and a shorter TTL. If the CBS was unreachable during the aggregation and you cached a partial result, the next request should re-attempt the fan-out sooner than it would for a complete result. Use a 15-second TTL for partial results versus 60 seconds for complete.

SAMA Open Banking compliance

The SAMA Open Banking Technical Specification v2.0 imposes several requirements on aggregation layer behaviour that are not obvious from reading the API spec alone:

  • Consent scope enforcement at the aggregator: The aggregation layer must enforce the account scope in the consent grant. If a TPP’s consent covers only current accounts, the aggregator must not fan out to the card processor even if the customer has a card. This requires the product registry lookup to intersect the customer’s product holding with the consented account types before constructing the target list.
  • Response staleness disclosure: When serving a cached result, the response must include a meta.dataRetrievedAt field with the timestamp of the last live fetch. The SAMA spec does not mandate a maximum staleness, but regulators interpret ambiguous cases against the bank; keep staleness within the cache TTL and surface it in the response.
  • Audit log per aggregation call: Each fan-out must be logged with: the consent ID, customer pseudonym, target system list, per-system status and latency, and whether the response was partial. This log is the evidence trail for a SAMA inspection of an Open Banking incident.
  • Rate limit enforcement: The SAMA spec sets a maximum of 4 account-info requests per consent per hour from the same TPP. The aggregation layer must enforce this limit before fanning out — not just at the API gateway. Gateway rate-limit counters can be bypassed by replay attacks; the aggregation layer’s enforcement is the backstop.
Account scope in SAMA OB v2 uses resource IDs, not types

SAMA Open Banking v2 consent grants reference specific account resource IDs (the bank-assigned account identifiers) rather than account types. This means your product registry lookup must map resource IDs to systems — not types to systems — and your aggregation must only fan out to systems that hold at least one resource ID from the consent grant. A consent for account SA8450000012345678 (a CBS current account) must not trigger a card-processor call, even though the customer has cards. The registry design must support per-resource-ID system mapping, not just per-product-type.

Performance & scalability

Scatter-gather is I/O-bound, not CPU-bound. The scalability ceiling is the number of concurrent downstream connections you can hold open, which is a function of connection pool sizes, the downstream systems’ own concurrency limits, and the number of concurrent Open Banking sessions.

At 500 concurrent Open Banking sessions fanning out to 3 systems each, the aggregation layer needs to sustain 1,500 concurrent outbound connections. Each downstream must have a connection pool sized to absorb that load without queueing. For the legacy CBS on a mainframe, 1,500 concurrent CICS connections is likely above its capacity — this is the most common scalability limit discovered during load testing. The remediation is to introduce a request queue at the CBS adapter with a maximum queue depth, circuit break when the queue fills, and serve partial results from the other two systems. The CBS adapter becomes the pacing element for the entire aggregation; size its connection pool and queue depth in coordination with the mainframe team.

CBS adapter connection pool Max concurrent CICS connections 150–200 (mainframe-limited; queue remainder)
Digital core adapter HTTP connection pool per pod 400 (REST API; modern platform)
Card adapter connection pool SOAP/HTTP connections 250 (legacy constraint from card processor)

What production tells you

Three things appear in every scatter-gather production deployment at a KSA bank that engineering teams do not predict during design.

The slowest downstream defines your p99, not your average. If the CBS takes 1,800ms p99 on working days during peak hours, your scatter-gather response time p99 is 1,800ms regardless of how fast the other three systems are. Optimising the digital core from 100ms to 80ms makes no measurable difference to the customer. The only optimisation that matters for latency is reducing CBS response time — which usually requires CBS-side caching or indexing changes, not changes to the aggregation layer.

Consent-scope enforcement bugs produce phantom data. The most common production incident after go-live is a TPP receiving account data outside the consented scope — not because of a security breach, but because the product registry lookup was incorrect and fanned out to a system that holds an account the consent does not cover. The result is a customer complaint that the finance app shows an account they did not expect. This is a consent enforcement bug, not a data breach, but it triggers a SAMA incident report. Test consent scope enforcement explicitly with accounts that partially overlap the consented scope; do not test only with fully-consented customers.

The partial-result flag is the most useful operational signal you have. When the CBS circuit breaker opens during a maintenance window, the partial-result flag in your logs tells you exactly which sessions were affected and which TPPs need to be notified. If you did not build the partial flag into your audit log at launch, you will reconstruct the blast radius of every CBS incident from raw logs, manually, while the incident is open. Build the flag; log it; alert on a threshold (e.g. more than 15% of sessions returning partial in any 5-minute window).
