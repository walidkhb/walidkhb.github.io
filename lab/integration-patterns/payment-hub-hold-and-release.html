Payment Hub to Core Banking: One Idempotent API and a Hold-and-Release State Machine

A payment hub knows the schemes. Core banking knows the money. Neither should learn the other’s job. The integration between them comes down to two core calls — verify-and-hold, then post-and-release — wrapped in one idempotent channel API and a state machine that says exactly what happens to a customer’s funds at every step, including the steps where something goes wrong.

Overview

A Saudi bank brings in a new payment hub to run its rails: instant payments, SARIE, SADAD bill payments, bulk files and request-to-pay. The hub builds and parses ISO 20022 messages, talks to the schemes and tracks scheme status. It does not hold accounts. Core banking holds the accounts, the balances, the holds and the ledger. It knows nothing about schemes.

Between them sits an integration layer. Its job is narrow and it should stay narrow: translate protocols, correlate requests and replies, enforce idempotency, and protect core banking with circuit breakers and retries. It holds no payment business logic and no accounting. It owns three things the other two systems cannot own well: the channel contract, the idempotency record, and the routing decision of which engine handles a given payment.

This article covers the mechanics. The decision to migrate one rail at a time behind that unchanged contract — flags, dark launch, evidence-based cutover — is covered in the companion essay, Strangle the Rails, Not the Channels.

Three owners, three domains

The payment hub owns the payment lifecycle and scheme messaging. Core banking owns account state, holds and posting. The integration layer owns protocol translation, correlation, idempotency and resilience. When a design review cannot say in one sentence which of the three owns a field or a decision, stop and fix that first. Ambiguous ownership becomes duplicated logic, and duplicated logic becomes a reconciliation break.

The Core Banking Contract

Core banking exposes two operations for hub-driven payments. Everything else in this article is built on them.

  • Verify-and-hold. One synchronous call that validates the debit (account status, restrictions, limits, available balance) and places a hold for the amount. On success it returns a hold reference. Validation and reservation happen in the same call, so there is no window where funds were checked but not yet reserved.
  • Post, with two modes. Post-and-release books the debit and lifts the hold in one step. Release-only lifts the hold and books nothing. Both take the hold reference.

Some flows have no customer debit to reserve: inbound credits, scheme-initiated settlement, bulk file postings. These use a direct-post path with a zero hold reference. A useful way to see the whole surface is four routes:

RouteCallsHold referenceUsed when
A — hold then postverify-and-hold, then post-and-releaseRealCustomer-initiated debit that must be reserved before scheme submission
B — verify then postverify (no reservation), then postZeroCompliance or eligibility check without reserving funds, e.g. an inbound credit, or a payment funded outside the deposit account
C — direct postpost onlyZeroScheme-initiated entries: inbound files, returns, refunds, reversals after posting
D — release onlypost in release-only modeReleasedHold placed, but the payment will not complete: scheme reject, timeout, cancellation

Hold and post are separate commits

The two-phase design is not a distributed transaction. A hold can be placed and then orphaned if the second call never comes. Every hold therefore needs an owner who is guaranteed to issue either post-and-release or release-only. In this design that owner is the state machine below, backed by a sweeper that finds holds older than the scheme’s maximum response time and resolves them.

The Payment State Machine

Each scheme-bound transfer moves through the same states. Internal transfers that never leave the bank collapse to a single posted state, because there is no scheme leg to wait for.

Figure 1 — Transfer lifecycle. Every path out of HELD ends in exactly one core post call: post-and-release on acceptance, release-only on rejection or timeout. Reversal after posting is a new, compensating entry, not an undo.

Three properties make the machine safe.

  1. Terminal states are final

    POSTED, RELEASED, REJECTED and REVERSED accept no further transitions except POSTED → REVERSED. A late scheme message for a RELEASED payment does not move it back; it raises an exception case (see failure modes).

  2. Every transition has one trigger and one core side effect

    HELD is entered only by a successful verify-and-hold. RELEASED is entered only after release-only succeeds. If the core call fails, the state does not move; the retry policy decides what happens next.

  3. Reversal is a new entry

    When a recall (camt.056) arrives after posting, nothing is undone. A compensating entry is booked through the direct-post route. The original posting and the reversal both stay on the ledger, which is what auditors expect.

TransferState.javajava
public enum TransferState {
    RECEIVED, VALIDATING, HELD, SUBMITTED, SCHEME_PENDING,
    POSTED, RELEASED, REJECTED, REVERSED;

    private static final Map<TransferState, Set<TransferState>> ALLOWED = Map.of(
        RECEIVED,       Set.of(VALIDATING, REJECTED),
        VALIDATING,     Set.of(HELD, REJECTED),
        HELD,           Set.of(SUBMITTED, RELEASED),
        SUBMITTED,      Set.of(SCHEME_PENDING, RELEASED),
        SCHEME_PENDING, Set.of(POSTED, RELEASED),
        POSTED,         Set.of(REVERSED),
        RELEASED,       Set.of(),
        REJECTED,       Set.of(),
        REVERSED,       Set.of());

    public TransferState to(TransferState next) {
        if (!ALLOWED.get(this).contains(next)) {
            // Never "fix" an illegal transition in code. Raise a case for operations.
            throw new IllegalTransitionException(this, next);
        }
        return next;
    }
}

One Idempotent Channel API

Channels — mobile, internet banking, corporate portals, branch systems — call one transfer API. They do not know whether a payment goes to the hub or straight to core banking. That is the property that makes the migration possible later.

The general mechanics of idempotency keys (client-generated keys, request fingerprints, the atomic claim, TTL and cleanup) are covered in Idempotency Keys at Scale. This design follows that pattern. The points below are the decisions specific to a channel API sitting in front of two engines.

  • Namespace the key to the authenticated customer. The stored key is customerId + ":" + clientKey, where customerId comes from the verified token, never from the request body. Two customers who happen to generate the same key never collide, and one customer cannot probe for another customer’s cached response.
  • Check before any upstream call. The idempotency check runs before routing. A replay returns the cached response whether the original went to the hub or to core banking. Routing changes during a migration therefore cannot create a duplicate.
  • Same key, different payload is a conflict. This API returns 409 with a stable DUPLICATE_TRANSACTION code. The idempotency article argues for 422; either is defensible. What matters is that channels map by the error code, not the HTTP status.
  • Two states, one TTL. A new key is written as IN_FLIGHT with a 24-hour TTL, the request is forwarded, and the row becomes DONE with the response stored.
  • Legacy channels get a derived key. Channels that speak a fixed-length record format over IBM MQ cannot send a header. Their adapter derives the key deterministically from the channel identifier and the channel’s own message id, hashed with SHA-256. One derivation rule for every legacy channel; never a per-channel variant, or replay semantics fork.
idempotency-decision.txttext
lookup(customerId:key)
  absent                       -> write IN_FLIGHT (ttl 24h) -> route -> write DONE + response
  present, same hash, DONE     -> return cached status + body
  present, same hash, IN_FLIGHT-> 409 + Retry-After   (original still running)
  present, different hash      -> 409 DUPLICATE_TRANSACTION
  store unavailable            -> 503, do NOT forward  (fail closed)

Choosing the Idempotency Store

The first design put the idempotency record in Redis. It is fast, it has native TTLs, and SET NX gives an atomic claim. The design was changed to a relational database replicated with synchronous commit. The reasons are worth spelling out, because the same argument comes up on every payment programme.

ConcernRedis (async replication)Relational store, synchronous commit
Recovery point on failoverWrites acknowledged by the primary can be lost if it fails before replicating. An IN_FLIGHT marker can vanish.RPO 0. The commit is acknowledged only after the secondary has hardened it.
Read-modify-writeCheck, claim and update are separate commands or a script. Correct, but easy to get subtly wrong.Check-or-reserve and finalise are each one transaction, with row locks.
Related stateHold reference and lifecycle state live elsewhere.Idempotency row, hold reference and state can commit together.
LatencySub-millisecond.Single-digit milliseconds. Budget it: here, ≤10 ms p95.
AuditNeeds a separate durable trail.The table is the trail.

The deciding scenario is a failover in the middle of a payment. The integration layer claims the key, calls verify-and-hold, the hold succeeds — and the cache primary fails before the claim replicates. The channel retries. The new primary has no record of the key. A second hold is placed, and later possibly a second debit. A few milliseconds per request is a cheap price for removing that path.

check_or_reserve.sqlsql
-- One transaction: claim the key or report what is already there.
BEGIN;

SELECT state, payload_hash, response_code, response_body
  FROM idempotency_record
 WHERE scoped_key = :scoped_key
   AND expires_at > now()
   FOR UPDATE;                          -- blocks a concurrent duplicate

-- If no row: claim it.
INSERT INTO idempotency_record
       (scoped_key, payload_hash, state, created_at, expires_at)
VALUES (:scoped_key, :payload_hash, 'IN_FLIGHT', now(), now() + interval '24 hours');

COMMIT;

-- After the upstream call: finalise in a second short transaction.
UPDATE idempotency_record
   SET state = 'DONE', response_code = :code, response_body = :body,
       hold_reference = :hold_ref, completed_at = now()
 WHERE scoped_key = :scoped_key AND state = 'IN_FLIGHT';
Fail closed when the store is down

If the idempotency store cannot be reached, reject the write with 503 and page someone. Do not “degrade gracefully” by skipping the check. A declined payment is an inconvenience the customer can retry. A duplicate debit is an incident, a complaint and a reconciliation task. The residual risk becomes an availability dependency on the store — which is why it runs with synchronous secondaries, automatic failover and readiness probes that take the integration pods out of rotation while it recovers.

Deriving the Accounting-Event Catalogue

Every post call carries an accounting event. The event tells core banking which accounts to debit and credit. The catalogue of events is a contract between the integration team and finance operations, and it is where this kind of programme quietly loses months.

The first catalogue had 11 events. It was written by walking through the payment flows the team knew best. Implementation found the gaps one by one: outbound scheme flows had no customer-debit event at all; bill payments funded from a credit or prepaid card were missing entirely; and interbank refund settlement had no events defined. The catalogue grew to 28 — purely additive, nothing renamed — but each discovery cost a round trip with operations and a core configuration change.

The lesson is a method, not a number. Derive the catalogue from a matrix, not from a walkthrough. The axes are payment type, funding source and lifecycle outcome. Every non-empty cell needs an event, or an explicit “not applicable” with a reason.

Bill paymentCredit cardDebit card pool, credit biller + fee itemn/a (verify only)Mirror entry, funding-aware

Two details from the card-funded rows generalise well.

  • Funding source is a bank concern, not a scheme concern. The bill-payment scheme has no idea whether the customer paid from a card or an account. So the hub stays agnostic: the integration layer carries the funding source from the channel session and adds it to the verify call, and core banking picks the event. Adding a new funding type later is a core and integration change with no hub scope.
  • Two-system posting needs a daily control. For card-funded payments core banking posts against a card settlement pool account, while the card platform posts the customer-level debit. The sum of card-platform debits must equal the sum of pool debits each day. Any gap is a duplicate or a fraud signal, and it goes to operations.

Resilience Settings

Two upstreams, two sets of limits. Core banking is reached over IBM MQ with request/reply correlation; the hub is reached over REST with mTLS. The settings below are a reasonable starting point. Tune them against measured latency, not intuition.

resilience.yamlyaml
resilience4j:
  circuitbreaker:
    instances:
      core-banking:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 20            # last 20 calls
        failure-rate-threshold: 50         # open at 50% failures
        wait-duration-in-open-state: 30s
        permitted-number-of-calls-in-half-open-state: 3
      payment-hub:
        base-config: core-banking
  timelimiter:
    instances:
      core-banking: { timeout-duration: 8s }    # MQ request/reply
      payment-hub:  { timeout-duration: 10s }
  retry:
    instances:
      idempotent-only:
        max-attempts: 3
        wait-duration: 1s
        exponential-backoff-multiplier: 2  # 1s, 2s, 4s
        randomized-wait-factor: 0.25      # jitter
  • Retry only what is safe to retry. Verify-and-hold and post are retried only because both carry an idempotency key that core banking honours, and the post is keyed on the hold reference. A call that is not idempotent end to end gets no automatic retry.
  • One breaker per upstream. A slow hub must not trip the breaker that protects core banking, and the other way round.
  • Timeouts are part of the state machine. If the hub does not accept a submission within its timeout, the integration layer issues release-only with reason TIMEOUT. The customer’s funds are not left reserved behind an unknown outcome.
  • An open breaker is an answer. Channels get 503 UPSTREAM_UNAVAILABLE quickly. That is better than holding a connection for eight seconds to learn the same thing.

Per-Scheme Routing

A single router decides, per call, which engine handles a payment. Two ingress adapters feed it: REST for modern channels and fixed-length-over-MQ for legacy ones. Both normalise to one canonical payload, so the router has exactly one implementation. The routing table is data, not code.

scheme-routing.yamlyaml
routing:
  default: core                    # anything unlisted stays on core banking
  schemes:
    instant:        { route: hub,  shadow: none }
    request-to-pay: { route: hub,  shadow: none }
    bill-payment:   { route: hub,  shadow: core }   # soaking: legacy kept as shadow
    rtgs:           { route: core, shadow: hub  }   # dark launch: hub compared, not trusted
  dark-launch:
    compare-fields: [decision, amount, accountingEvent, postingItems, errorCode]
    shadow-side-effects: forbidden   # shadow path never holds or posts
    cutover-threshold: 0.001        # < 0.1% discrepancies over the window

Three rules keep this honest. The route is resolved once, at RECEIVED, and stored on the payment, so an in-flight payment finishes on the engine it started on even if the flag flips mid-flight. The shadow path runs in a no-side-effect mode: it computes what it would hold and post, and the comparison runs on those outputs. And turning a flag off is the rollback — for new payments only. Why the cutover is governed by evidence rather than a date is the subject of the companion essay.

Failure Modes

Late acceptance after the hold was released

The outbound timer expires, the integration layer releases the hold, and the payment is RELEASED. Then a delayed pacs.002 arrives with ACCP. The scheme has settled the money; the customer has not been debited. The state machine must not resurrect the payment. Route the late status to an exception queue, book the debit through the direct-post route under a dedicated event, and notify the customer. Size the outbound timer from the scheme’s documented maximum, not from your own SLA, and measure how often this case occurs.

Post succeeded, response lost

Core banking books the debit and releases the hold, but the MQ reply never arrives within the timeout. A naive retry of post-and-release could book twice. Two defences: the post is idempotent on the hold reference (a second post against an already-consumed hold must return the original result, not post again), and the retry first asks core banking for the hold’s status. Test this explicitly by dropping replies in a non-production environment.

Keys stuck IN_FLIGHT

If an integration pod dies between claiming a key and finalising it, the row stays IN_FLIGHT and every retry gets 409 for up to 24 hours. Run a recovery job that finds IN_FLIGHT rows older than the maximum end-to-end timeout, resolves the true outcome from the payment state and the core hold status, and finalises the row. Never just delete it.

Orphaned holds

A hold placed, then neither posted nor released, reduces the customer’s available balance for no reason. Causes include a crash between HELD and SUBMITTED and an unhandled hub error. A sweeper compares open holds against payment states every few minutes and resolves any hold whose payment is terminal or older than the scheme window. Alert on the count, not just on errors.

Shadow path with side effects

The most expensive dark-launch mistake is a shadow call that places a real hold or a real posting. The customer sees two reservations; the ledger may see two debits. Enforce no-side-effect mode in the router, not by convention in each flow, and test it with a balance check before and after a shadowed payment.

Accounting event missing for a new combination

A new funding source or payment type goes live without its event, and posts fail with a configuration error at the core. Make the matrix a release gate: a combination cannot be enabled in routing until every cell has a configured, tested event.

Production Checklist

  1. Write down the three owners

    Hub: lifecycle and scheme messaging. Core: accounts, holds, posting. Integration layer: translation, correlation, idempotency, resilience, routing. Review every new field against that list.

  2. Encode the state machine as an allowed-transition table

    Reject illegal transitions loudly. Make sure every exit from HELD ends in exactly one post call, in one of its two modes.

  3. Build the accounting matrix before the flows

    Payment type × funding source × outcome. Get operations to mark each event as existing or to be created, then treat the matrix as a release gate.

  4. Put idempotency in a synchronous-commit store and fail closed

    Namespace keys to the authenticated customer. Check before routing. Budget the latency. Rehearse a store failover during a load test and confirm no duplicates.

  5. Configure one breaker and one timeout per upstream

    Retry only idempotent calls, with backoff and jitter. On hub submission timeout, release the hold.

  6. Run the sweepers

    One for orphaned holds, one for stuck IN_FLIGHT keys, one exception queue for late scheme statuses. Each has an owner and a runbook.

  7. Make routing data, and pin the route per payment

    One router, two ingress adapters, one canonical payload. Shadow mode with no side effects. Flags per scheme. Rehearse turning a flag off under load.

  8. Reconcile daily

    Hub payment states against core postings, open holds against non-terminal payments, and card-platform debits against card pool debits. A clean reconciliation is the only real proof the state machine works.
