Building a FAPI 2.0 Authorisation Server In-House That Passes Conformance

Reading the FAPI 2.0 profile is the easy part. Passing a regulator’s conformance suite is harder: every clause needs a place in code where it is enforced, and a test that proves it. This is how we built the bank side of the KSA Open Banking Standard in-house and reached 130 of 130 functional conformance tests in sandbox, plus a strict dry run against the OpenID Foundation FAPI 2.0 suite with zero failures.

Overview

The previous article covered what FAPI 2.0 asks for. This one covers what it takes to prove you deliver it. The target was the bank side of the KSA Open Banking Standard: an authorisation server, account information APIs and payment initiation APIs. The bar was the regulator’s functional conformance suite, which plays the third-party provider (TPP) and attacks every rule in the profile.

The result, in sandbox:

SuiteResult
SAMA functional conformance — Account Information67 / 67
SAMA functional conformance — Payment Initiation, suite 132 / 32
SAMA functional conformance — Payment Initiation, suite 231 / 31
OpenID Foundation FAPI 2.0 Message Signing, strict dry run (private_key_jwt and mTLS client auth)0 failures

That is 130 of 130 functional tests. These are sandbox results, not a certification. The certification programme is under way. What follows is the build: the architecture choice, how each rule maps to one enforcement point, how we drove the conformance runner without a human, and what broke.

Conformance is a test of enforcement, not of features

Most conformance tests are negative. They send a request object with an expired exp, a token without the bound certificate, a PKCE verifier that does not match, a scope for someone else’s consent. A server that implements the happy path passes perhaps a third of the suite. The rest is about saying no in exactly the way the standard says to.

One Deployable, On Purpose

The obvious design splits the authorisation server, the consent service and the resource APIs into separate services. We did the opposite. The authorisation server and the resource APIs ship as one deployable and share the consent store in-process.

The reason is trust. In FAPI, the consent ties everything together. The PAR request references it. The scope carries its ID. The token is bound to it. The resource API checks it on every call. Split those across services and you must secure every hop between them: service credentials, token introspection, cache coherence on consent status. None of that is in the standard, and all of it is attack surface. With one process, a consent revoked at 10:00:00 is revoked for the token endpoint and the resource API at the same instant. There is no service-to-service trust to get wrong.

Inside the deployable, the packages stay strict: authz (PAR, authorise, token, PSU login and consent screens), common (signed bodies, schema validation, error model, mTLS bridge), core (consent store, back-end adapter) and one package per API family. You can split it later along those lines if load demands it. Conformance does not.

Figure 1 — One deployable on purpose: the gateway terminates TLS and forwards the verified client certificate; the authorisation server and resource APIs share the consent store in-process

mTLS: Split Between Gateway and App

Certificate handling has two jobs, and we gave them to two layers. The gateway does cryptography: it terminates TLS, verifies the TPP certificate chain against the trusted CA, and forwards the verified certificate to the app. The app does policy: it decides which endpoints need a certificate, binds tokens to its thumbprint, and authenticates tls_client_auth clients by subject.

Why not require the certificate at the TLS layer for everything? Because the PSU browser hits the same host for login and consent, and a browser has no client certificate. So the gateway asks for a certificate but does not demand one. The app then demands it where the profile does.

gateway.confnginx
server {
    listen 443 ssl;
    server_name as.sandbox.example;

    ssl_protocols TLSv1.2 TLSv1.3;
    # FAPI-permitted TLS 1.2 suites only
    ssl_ciphers ECDHE-RSA-AES128-GCM-SHA256:ECDHE-RSA-AES256-GCM-SHA384:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384;

    ssl_client_certificate /etc/gateway/tpp-ca.pem;
    ssl_verify_client      optional;   # browsers share this host
    ssl_verify_depth       3;

    location / {
        # proxy_set_header replaces any inbound value: a client cannot
        # smuggle its own certificate header past the gateway.
        proxy_set_header X-Client-Cert-Verify $ssl_client_verify;
        proxy_set_header X-Client-Cert        $ssl_client_escaped_cert;
        proxy_set_header X-Forwarded-Proto    https;
        proxy_pass http://app:8080;
    }
}
The forwarded certificate header is a credential

If the app trusts X-Client-Cert and anything other than the gateway can reach the app, anyone can claim any certificate. Overwrite the header at the gateway on every request, check X-Client-Cert-Verify equals SUCCESS before using it, and make sure the app port is reachable only from the gateway. This is the one place where the single-deployable design still needs network trust.

Enforcement in Code

Spring Authorization Server gives you most of OAuth. The FAPI and KSA rules sit on top as converters, validators and filters. Four of them carry most of the weight.

Request object: trust only what is signed

At /par, the form may carry a request parameter plus loose parameters. The profile says only the signed request object counts. So the converter verifies it, checks the time windows, and rebuilds the authorisation request from its claims alone.

RequestObjectValidator.javajava
public final class RequestObjectValidator {

    private final String issuer;
    private final Duration maxAge;     // 60 min or 10 min, by profile version
    private final Clock clock;

    JWTClaimsSet validate(SignedJWT jwt, RegisteredClient client) throws ParseException {
        if (!"oauth-authz-req+jwt".equals(typ(jwt)))      fail("typ");
        if (!JWSAlgorithm.PS256.equals(jwt.getHeader().getAlgorithm())) fail("alg");
        if (!verify(jwt, client.jwks()))                    fail("signature");

        JWTClaimsSet c = jwt.getJWTClaimsSet();
        Instant now = clock.instant();
        Instant nbf = required(c.getNotBeforeTime(), "nbf").toInstant();
        Instant exp = required(c.getExpirationTime(), "exp").toInstant();

        if (!c.getAudience().equals(List.of(issuer)))        fail("aud");
        if (!client.id().equals(c.getIssuer()))               fail("iss");
        if (nbf.isBefore(now.minus(maxAge)))                    fail("nbf too old");
        if (Duration.between(nbf, exp).compareTo(maxAge) > 0)  fail("exp - nbf");
        if (!exp.isAfter(now))                                fail("expired");
        return c;   // caller builds the request from these claims only
    }

    private static void fail(String what) {
        throw new OAuth2AuthenticationException(
            new OAuth2Error("invalid_request_object", what, null));
    }
}

Certificate-bound tokens and consent-bound refresh

Access tokens live five minutes and carry the certificate thumbprint. Refresh tokens are the opposite of the usual advice: they are not rotated, and they live exactly as long as the consent. A TPP that refreshes daily for a one-year consent keeps one refresh token. Revoke the consent and the refresh token dies with it.

TokenPolicy.javajava
TokenSettings fapiTokenSettings() {
    return TokenSettings.builder()
        .accessTokenFormat(OAuth2TokenFormat.SELF_CONTAINED)
        .accessTokenTimeToLive(Duration.ofMinutes(5))
        .x509CertificateBoundAccessTokens(true)   // cnf.x5t#S256
        .reuseRefreshTokens(true)                 // profile: no rotation
        .build();
}

// Refresh token expiry follows the consent, not a fixed TTL.
final class ConsentBoundRefreshTokenGenerator
        implements OAuth2TokenGenerator<OAuth2RefreshToken> {

    private final ConsentStore consents;

    public OAuth2RefreshToken generate(OAuth2TokenContext ctx) {
        if (!OAuth2TokenType.REFRESH_TOKEN.equals(ctx.getTokenType())) return null;
        Consent consent = consents.fromScopes(ctx.getAuthorizedScopes());
        Instant now = Instant.now();
        return new OAuth2RefreshToken(randomToken(), now, consent.expiresAt());
    }
}

Parameterised scopes

In the KSA profile the scope is not just accounts. It is accounts:<ConsentId>. That turns the scope into a pointer. The validator must check that the pointer is real, in the right state, and owned by the calling client. Skip the ownership check and one TPP can authorise against another TPP’s consent.

ConsentScopeValidator.javajava
private static final Pattern SCOPE =
    Pattern.compile("^(accounts|payments):([A-Za-z0-9\\-]{1,128})$");

Consent resolve(Set<String> scopes, String clientId) {
    List<Matcher> hits = scopes.stream().map(SCOPE::matcher)
        .filter(Matcher::matches).toList();
    if (hits.size() != 1) throw invalidScope("exactly one consent scope");

    Matcher m = hits.get(0);
    Consent c = consents.find(m.group(2))
        .orElseThrow(() -> invalidScope("unknown consent"));

    if (!c.family().equals(m.group(1)))      throw invalidScope("wrong family");
    if (!c.clientId().equals(clientId))       throw invalidScope("not your consent");
    if (c.status() != Status.AWAITING_AUTHORISATION) throw invalidScope("bad state");
    return c;
}

Schemas straight from the standard

We did not hand-write a single payload rule. The standard publishes OpenAPI files; the validator loads them at start-up and checks every request and response body against the matching operation. When the standard moves to a new errata, we drop in the new files and the tests tell us what changed. Hand-coded validation would have drifted within a month.

Validate responses too, in sandbox

Conformance suites check what you send back as strictly as what you accept. Running response validation in sandbox caught date formats, missing mandatory links and enum casing in our own output before the suite did. Keep it on in test. Decide separately whether the cost is worth it in production.

Driving Conformance Headlessly

The regulator’s suite is built for a person at a browser: restart, paste discovery and config, fetch test cases, approve each PSU consent by hand, start the run, read the verdicts. One full pass by hand took most of a morning. We needed it on every change.

So we scripted the same steps the manual guide describes, in the same order. Nothing in the suite was modified; the script only clicks the buttons a person would.

  1. Restart the runner

    The suite expects a clean start for each test set. The script restarts it and waits for its health endpoint, rather than trusting a fixed sleep.

  2. Load discovery and configuration

    The config is generated, not edited. A small tool reads the suite’s own discovery templates, points them at the sandbox, and writes in the client certificates and signing keys. Keys never enter version control.

  3. Stage consents

    Fetching the test cases makes the suite create its consents and PAR requests. The script collects the authorisation URLs it produces.

  4. Complete each PSU consent

    A headless browser opens each URL on the sandbox, logs in as a test PSU, selects accounts, and approves. Negative cases that expect a rejection are left to fail as designed.

  5. Hand back callbacks and run

    The redirects land at the suite. The script starts the run and waits for completion.

  6. Collect verdicts

    Results are parsed into one JSON file per plan and compared with the previous run. A test that flips from pass to fail breaks the build.

run-conformance.tstypescript
export async function runPlan(plan: Plan): Promise<Verdicts> {
  await runner.restart();
  await waitUntil(() => runner.healthy(), { timeoutMs: 120_000 });

  await runner.loadDiscovery(await readJson(`out/discovery-${plan}.json`));
  await runner.loadConfig(await readJson("out/config.json"));   // generated, gitignored

  const cases = await runner.fetchTestCases();             // stages consents + PAR
  for (const c of cases.filter(c => c.authorizeUrl)) {
    await psu.completeConsent(c.authorizeUrl, psuFor(c));      // headless browser
  }

  await runner.start();
  await waitUntil(() => runner.finished(), { timeoutMs: 30 * 60_000 });

  const verdicts = parseVerdicts(await runner.log());
  await writeJson(`out/results-${plan}.json`, verdicts);
  return verdicts;
}

A full set of three plans now runs unattended in well under an hour. That changed how we worked. We stopped batching fixes for a “conformance day” and started treating a red test like a failing unit test.

Automation is for iteration; the submission is still manual

The official evidence package comes from the suite’s own UI and carries a signed declaration from the implementer. The headless runner gets you to green quickly. A person still runs the final pass and signs.

Compatibility Switches vs Strict Mode

Test tools are software. Where a conformance tool behaves differently from the profile text, you have two bad options: fail a test you should pass, or weaken a check you should keep. We took a third. Each difference got a named switch, a default for the functional suite, and a strict value for everything else.

application-conformance.yamlyaml
fapi:
  profile:
    # The KSA profile asks for aud = issuer. FAPI 2.0 also allows the token
    # endpoint URL. Accept both unless strict.
    strict-assertion-audience: false

    # Request-object window. One profile version allows 60 minutes,
    # the OpenID Foundation KSA profile requires 10. Config, not code.
    request-object-max-age: 60m

  compat:
    # Test-data identity check relaxed for the functional suite only.
    enforce-psu-identity-match: false
    # Tolerates a conformance-tool quirk; logged on every use.
    conformance-tool-quirk: true

---
# Strict profile: OpenID Foundation runs and anything that is not the functional suite.
spring.config.activate.on-profile: strict
fapi:
  profile:
    strict-assertion-audience: true
    request-object-max-age: 10m
  compat:
    enforce-psu-identity-match: true
    conformance-tool-quirk: false

Three rules kept this honest. Every switch is logged at start-up with its value. Every relaxed check logs a warning each time it is used. And the OpenID Foundation dry run, against both private_key_jwt and mTLS client authentication, runs in strict mode only. Zero failures there is the evidence that the switches are compatibility shims, not hidden weaknesses.

A compatibility switch must never reach production at its relaxed value

Make strict the default in the base configuration and relax only in a named conformance profile. Fail start-up if the relaxed profile is active together with a production marker. A switch that “someone will flip later” is a finding waiting to happen.

What Broke

Most failures were not in cryptography. They were in edges: windows, encodings, and places where two readings of the text were both reasonable.

SymptomCauseFix
Token-binding tests failed only behind the gatewayThe forwarded certificate was PEM with URL encoding; the app parsed it rawOne certificate bridge filter decodes it once; everything downstream reads a parsed X509Certificate
Refresh tests failed after the first refreshLibrary default rotated refresh tokensReuse refresh tokens; tie expiry to the consent
Error-path tests failed despite the right statusBody returned on 401 where the profile wants header-onlySingle exception handler that chooses body or header by status
Request-object tests passed in one suite, failed in the otherTwo profile versions disagree on the time windowWindow moved to configuration; strict profile uses the tighter value
Client-assertion tests rejected valid clientsaud checked as issuer only; tool sent the token endpointAccept both by default, as FAPI 2.0 permits; issuer-only in strict
Interaction-ID tests failed on error responsesFilter ran after the exception handlerFilter ordered first so every response carries x-fapi-interaction-id
Payment tests failed on signed responsesContent type returned as application/json for a JWS bodyCodec sets application/jwt and wraps the payload in the message claim
Flaky runsRunner state carried over between test setsRestart per set, health-wait instead of sleep

The pattern is clear in hindsight. Each failure came from a rule enforced in two places, or in none. The matrix fixed that more than any single line of code did.

Checklist

  1. Decide the deployable boundary by trust, not by org chart

    Keep the authorisation server and resource APIs together while consent is shared state. Split only when you can name who secures each new hop.

  2. Split mTLS: cryptography at the gateway, policy in the app

    Verify chains at the edge, overwrite the certificate header on every request, and require the certificate per endpoint in the app.

  3. Write the rule → enforcement matrix before the code

    One row per profile rule, one enforcement point per row, and the conformance tests that cover it. Review it with every profile errata.

  4. Generate validation from the standard’s OpenAPI

    Validate requests and responses against the published schemas. Do not hand-code payload rules.

  5. Make time windows and audiences configuration

    Request-object age, exp − nbf, token lifetime and assertion audience will differ between profile versions and suites.

  6. Automate the conformance runner on day one

    Script the manual guide step by step. Store verdicts per run and fail the build on any regression.

  7. Name every compatibility switch and prove strict mode

    Strict by default, relaxed only in a named profile, logged on use. Run the OpenID Foundation suite in strict mode and expect zero failures.

  8. Say what the result is

    Sandbox conformance is not certification. Report it as what it is, and keep the certification evidence path separate and manual.
