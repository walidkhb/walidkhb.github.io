Legacy Integration: Generated Business APIs & a Wire-Protocol Core Simulator

A core banking system exposed as 934 fixed-length messages is not an interface. It is a puzzle every consumer solves again. This article shows how to turn those messages into 14 governed business APIs by generation, not by hand — and how a simulator that speaks the real wire protocol, plus data-driven contract tests, removed the core as the bottleneck for every test cycle.

Overview

Many banks still reach their core through fixed-length messages over IBM MQ. A fixed header. A body laid out byte by byte. Amounts in the lowest currency unit. Field names abbreviated to six or eight characters. Result codes in two parts. Bodies in EBCDIC or ASCII depending on who sent them.

At a Saudi bank, every consumer had learned this format on its own. Each one re-implemented the same layouts. Each one hit the same defects. The knowledge sat with a handful of people. And every test cycle queued for the one shared core test environment.

The fix had three parts:

  • A machine-readable catalogue of every request and response layout — 934 transaction codes, 1,866 layouts.
  • A generator that combines the catalogue with a reviewed design layer and emits 14 OpenAPI 3.1 contracts (about 1,280 operations), 96 business flows, internal field mappings and DFDL models. A thin adapter on IBM ACE runs them.
  • A core simulator on the same runtime that speaks the real wire protocol for all 934 codes, plus a deterministic test generator that produced 6,256 contract test cases.

The COBOL data mapping article covers how DFDL parses one copybook. This article is about the step above: treating the whole message estate as data, and generating everything else from it.

Figure 1 — The catalogue and the reviewed design layer are the only hand-maintained inputs. The generator emits contracts, flows, internal mappings and DFDL models. The adapter can call the real core or the simulator; the test harness drives both through the business APIs.

The Message Catalogue

Everything starts with one decision: layouts are data, not documents. The interface specifications describe each message as a table. A parser reads the tables and writes one JSON catalogue. Each entry holds the code, the title, the direction, every field with its type and length, and the declared total.

Repeating groups, shared structures and the header become references, not copies. A layout is only accepted when the computed length matches a declared length. Anything else needs a recorded decision.

catalogue.json (excerpt, illustrative names)json
{
  "code": "T41200",
  "title": "Account-to-account transfer",
  "domain": "payments",
  "request": {
    "declaredBody": 128,
    "fields": [
      { "name": "DBTACC", "type": "n",  "len": 13 },
      { "name": "CRDACC", "type": "n",  "len": 13 },
      { "name": "TXNAMT", "type": "ns", "len": 15, "signByte": true },
      { "name": "TXNCCY", "type": "a",  "len": 3 },
      { "name": "CHNREF", "type": "an", "len": 32 },
      { "name": "FILLER", "type": "an", "len": 51, "reserved": true }
    ],
    "computedBody": 128,
    "status": "length-validated"
  }
}

The status field is the important one. A layout is length-validated, a hand-verified override, or a documented spec error. Nothing is left unresolved. The rule is simple: if the field list is internally consistent and the declared total is wrong, the field list wins and the defect is recorded.

What Compiling the Specs Found

Nobody had ever checked every table against its own arithmetic. A compiler does that on day one. Across 1,866 layouts, the check surfaced:

FindingScaleEffect on a consumer built from the document
Wrong declared totals96 layoutsFields added or widened, total row never updated. A buffer sized from the total truncates or pads.
Undocumented trailing sign byteEvery signed numeric fieldA signed field of N digits occupies N + 1 bytes. The tables never say so; only the totals prove it. Every field after it shifts by one.
Reply length off by two bytesOne high-volume replyFields sum to two bytes more than declared. A consumer reading by declared offsets reads the wrong bytes.
Wrong codes in headingsA handfulA table labelled with the code of a different message.
Hand corrections neededAbout 30Draft tables, duplicated fields, impossible structures.
The defects were already in production — in every consumer

Each consumer had met these defects separately and patched around them. Some patches disagreed. That is the real cost of undocumented direct access: the same bug, fixed differently, in many places. A defect register sent to the core team, plus overrides recorded with their reasoning, turns tribal knowledge into one reviewed source. Every override stays open until the core owner confirms the reading.

Options Compared

With a full catalogue, four ways to expose the core were on the table.

A. Direct callsB. Generic pass-throughC. Generated domain APIs, thin adapterD. Full domain services
Consumer effortHigh, repeatedMedium — still core semanticsLowLow
Contract qualityNoneCore field names leak into every consumerBusiness English, ISO formats, one outcome modelBest
ReplaceabilityNoneNone — the contract is the coreHigh — the contract is independentHigh
Build effort—LowMedium — generator plus reviewVery high
Where logic livesConsumersConsumersCore, unchangedNew services — duplicates the core

Option C won. One API per business domain. The adapter maps names and formats, builds the header, does request–reply over MQ, maps outcomes and keeps an idempotency store. Balances, limits, eligibility and pricing stay in the core. The adapter adds no rules.

That gives replaceability without duplicating logic. The contract never names a core field, code or format. Any system that can answer the same operations can sit behind the same APIs.

The Design Layer

A catalogue alone produces mechanical APIs. POST /t41200 with a body of abbreviations helps nobody. The design layer is the small, reviewed set of decisions a person must make:

  • Operation per code — name, HTTP method, resource path, audience (public or internal), or exclusion with a reason.
  • Vocabulary — abbreviation fragments to English words, with per-field overrides where the mechanical result reads badly.
  • Flows — which operations chain into a business flow, such as verify → post → reverse.
design/operations/payments.json + vocabulary.json (illustrative)json
// operations: one decision per transaction code
{
  "T41200": {
    "operationId": "createAccountTransfer",
    "method": "POST",
    "path": "/account-transfers",
    "audience": "public",
    "timeoutMs": 20000
  },
  "T90010": { "exclude": "technical heartbeat, no business meaning" }
}

// vocabulary: fragments first, field overrides win
{
  "fragments": { "DBT": "debit", "CRD": "credit", "ACC": "account",
                 "TXN": "transaction", "AMT": "amount", "CCY": "currency" },
  "overrides": { "CHNREF": "channelReference",
                 "DBTACC": "debitAccountNumber" }
}

Of the 934 codes, 705 became public operations and 155 internal ones. 74 technical codes were excluded, each with a written reason. The design files are the governed source. They go through review per domain, like any other architecture artefact.

The Generator

The generator is deterministic. Same inputs, same bytes out. It produces four artefact families from the catalogue plus the design layer:

ArtefactAudienceContent
14 OpenAPI 3.1 contractsPublic / consumersAbout 1,280 HTTP operations, schemas, examples, headers, outcome envelope. Validated on every run.
96 business flowsPublic / consumersSequence diagrams of operations; six also published as single-call composite operations.
Field mappingsInternal low-level design onlyBusiness field ↔ core field, type, length, conversion, per operation. Readable and machine-loadable.
DFDL modelsAdapter and simulatorOne static library per business domain plus a core library for the header, so a flow references only what it uses.

The last step of every run is a leak check. Public contracts must carry no core field names, no transaction codes, no document references. The check fails the build if any appear.

generate.py (sketch)python
def build_property(field, vocab):
    # Reserved and filler fields are never exposed.
    if field.get("reserved"):
        return None
    name = vocab["overrides"].get(field["name"]) or camel(
        [vocab["fragments"][f] for f in split_fragments(field["name"])])
    schema = FORMAT_RULES[field["type"]](field)   # amount -> decimal string, date -> ISO
    return name, schema

def leak_check(spec_text, catalogue):
    forbidden = catalogue.all_field_names() | catalogue.all_codes()
    hits = [t for t in forbidden if re.search(rf"\b{re.escape(t)}\b", spec_text)]
    if hits:
        raise SystemExit(f"core names leaked into public contract: {sorted(hits)[:10]}")

for domain in DOMAINS:
    spec = render_openapi(domain, catalogue, design, vocab)
    leak_check(spec, catalogue)
    validate_openapi(spec)                      # fail fast on invalid 3.1
    write(f"api-specs/{domain}.yaml", spec)
    write(f"lld/mapping/{domain}.json", render_mapping(domain))  # internal only
    write_dfdl_library(domain, catalogue)
Generated files are never hand-edited

The day someone fixes a contract by hand, the generator and the contract disagree. The next run silently reverts the fix, or someone stops running the generator. Both end the same way: 14 contracts drifting apart. Make the rule mechanical. A pipeline step regenerates and diffs; any difference fails the build. If a contract is wrong, fix the catalogue, an override or the design layer.

Contract & Outcome Model

The conventions are few and strict. Base path /{domain}/v1. Plural kebab-case resources. Commands take an idempotency key. Amounts are decimal strings with 0–3 decimals by ISO 4217 currency. Dates are ISO dates. Y/N flags become booleans. A count plus a repeating group becomes a JSON array.

The most debated rule was the outcome model. A core that answers “insufficient funds” has worked correctly. That is a business outcome, not an error. So:

  • Bank declines are HTTP 2xx with status: FAILED and a failureDetails category.
  • RFC 7807 problem details are only for protocol failures — validation (400), auth (401/403), conflicts (409), throttling (429), and upstream trouble (502/503/504).
business decline vs protocol failurejson
// 201 Created — the bank declined; the call itself succeeded
{
  "status": "FAILED",
  "failureDetails": {
    "category": "INSUFFICIENT_FUNDS",
    "message": "Available balance is lower than the transfer amount.",
    "backendSystem": "CORE_BANKING",
    "retryable": false
  },
  "data": { "accountTransferId": "5b0e…" },
  "meta": { "bankReference": "…" }
}

// 504 Gateway Timeout — application/problem+json; outcome unknown
{
  "type": "https://api.example.test/problems/backend-timeout",
  "title": "No reply from core banking within the operation timeout",
  "status": 504,
  "detail": "Retry with the same X-Idempotency-Key."
}

The mapping from core result codes to outcomes is itself generated from the documented codes into a versioned table. A partial-success action maps to COMPLETED with warnings. Any undocumented code falls to a generic decline and is logged for review. A 504 means the outcome is unknown: the caller retries with the same key, and the adapter resends with the core’s possible-duplicate flag set so the core replays rather than re-posts.

Why declines are not errors

If a decline is a 4xx, every gateway, retry policy and dashboard treats it as a fault. Circuit breakers open on a run of insufficient-funds replies. Error-rate alerts fire on payday. Keep the transport signal and the business signal apart. Breakers count timeouts and unreadable replies, never FAILED outcomes.

The Core Simulator

Contracts are only half the story. Testing them needed the core, and the core had one shared test environment. Every project queued for it. Data was overwritten between teams. A missing seed account could stop a test cycle for days.

The simulator removed that queue. It runs on IBM ACE, the same runtime as the adapter, and is built only from DFDL models and ESQL. It listens on MQ and HTTP. It answers all 934 codes with the real wire format. The adapter cannot tell the difference, which is the point.

Encoding from the bytes

Some consumers send EBCDIC, others ASCII. The simulator does not trust headers or configuration. The transaction code is numeric, and numeric digits look different in each encoding. One byte decides. The reply uses the same code page, and the MQ descriptor is set to match.

SimCore.esql (sketch)esql
CREATE FUNCTION DetectCcsid(IN frame BLOB) RETURNS INTEGER
BEGIN
  -- Digits are X'F0'..X'F9' in EBCDIC and X'30'..X'39' in ASCII.
  DECLARE b BLOB SUBSTRING(frame FROM CODE_OFFSET FOR 1);
  IF b >= X'F0' AND b <= X'F9' THEN
    RETURN 37;              -- EBCDIC
  END IF;
  RETURN ASCII_CCSID;        -- the bank's ASCII code page
END;

Generic reply construction

Writing 934 handlers was never an option. Instead, every reply is built the same way. The simulator serialises an empty reply from the DFDL model, parses it back so every field exists with a default, then fills each field by a fixed precedence:

  1. Echo — if the request has a field with the same name, copy it.
  2. Naming convention — for the customer, account or posting the request refers to, take the value the field name implies: available balance, currency, IBAN, name.
  3. Default — today’s date or timestamp, otherwise blank or zero.

Repeating groups expand from the matching entity list — a customer’s accounts, an account’s postings. This gives a well-formed, ledger-consistent reply for every code with no per-code logic.

SimResponder.esql (sketch)esql
CREATE PROCEDURE FillField(IN rsp REFERENCE, IN req REFERENCE,
                           IN acct REFERENCE, IN fld CHARACTER)
BEGIN
  -- 1. echo a request field with the same name
  IF FIELDTYPE(req.{fld}) IS NOT NULL THEN
    SET rsp.{fld} = req.{fld}; RETURN;
  END IF;
  -- 2. naming convention: the suffix says what the field holds
  CASE SUBSTRING(fld FROM LENGTH(fld) - 2)
    WHEN 'BAL' THEN SET rsp.{fld} = AvailableBalance(acct);
    WHEN 'CCY' THEN SET rsp.{fld} = acct.currency;
    WHEN 'IBN' THEN SET rsp.{fld} = acct.iban;
    WHEN 'DAT' THEN SET rsp.{fld} = TodayYmd();
    ELSE -- 3. leave the model default (blank or zero)
  END CASE;
END;

A ledger, not canned replies

Canned replies pass a happy-path test and nothing else. The simulator keeps a small stateful ledger seeded with fictitious customers and accounts in every interesting state — active, blocked, dormant, closed, debit-frozen, low balance, overdraft.

BehaviourWhat the simulator does
VerifyChecks status and available balance, places a hold for the amount.
PostReleases the hold and posts principal, charge and tax legs.
ReverseFinds the original by reference and posts the opposite entries. Rejects if not found or already reversed.
Repeat requestKey = code + channel reference. A plain repeat is rejected as a duplicate.
Possible-duplicate flagThe original reply is replayed, byte for byte. Nothing is posted twice.
MaintenanceAdd, modify and delete answer OK and are stored for inspection.
Fault rulesTimeouts, delays, forced rejections and field overrides, matched on code and field value.
Do not invent result codes silently

Some situations had no documented result code — hold not found, already reversed, duplicate reference. The simulator answers these in a reserved range that appears in no specification. The adapter maps that range to “pending core confirmation”, and each item sits on a review list for the core owner. Inventing plausible codes would have baked guesses into every consumer.

One honest limit: the simulator is consistent with its own ledger. It does not reproduce every business rule of the real core. It replaces the core for integration and contract testing. It does not replace end-to-end acceptance on the real core before go-live.

Data-Driven Contract Tests

Writing tests by hand for 1,280 operations does not scale. The test cases are generated, deterministically, from three inputs: the contracts, the internal mappings and the simulator seed. A filler knows how to build a valid request for any operation from a profile — a customer, their accounts, a card, a loan, a beneficiary.

Case typeWhat it proves
HappyA valid request reaches the core and maps back to a schema-valid response.
NegativeUnknown account, inactive account, insufficient funds — the right FAILED category.
ProtocolMissing headers, invalid body, wrong types — 400 problem details, nothing sent to the core.
FlowVerify → post → reverse, with balances checked before and after.
IdempotencySame key and body replays; same key and different body is 409.
OutcomeA stored outcome is retrievable later by its id.
LanguageAccept-Language: ar returns Arabic text, correctly encoded.
Timeout & forced rejectFault rules on the simulator: 504 with unknown outcome; a forced decline mapped correctly.

    "profile": "retail-low-balance",

}

The run has three phases. Main runs in parallel. Serial runs the balance-checked flows one at a time, because they assert exact balances. Scenario runs last: timeouts and forced rejections through simulator fault rules, each on a distinct code so it cannot disturb another case.

Schema mismatches are reported as findings, not failures. A mismatch usually means the catalogue, an override or the core disagree. That needs a decision, not a red build that people learn to ignore.

The total was 6,256 cases. A separate pass calls every one of the 934 codes raw on the simulator, then joins the results into a coverage matrix: reached through a business API, reached raw only, or not covered.

Production Traffic as Test Data

Seed data proves the mappings. Real traffic proves the edge cases nobody wrote down. A small masking tool takes exported channel logs that contain raw core messages and turns them into test data, inside the bank network only.

  • Each message is split into fields using its layout from the catalogue. Each field is classified by name and description.
  • Replacements keep length and format, and are deterministic under a key. The same customer maps to the same test customer everywhere, so linked flows stay linked.
  • Card numbers move to a test range with valid check digits. Identity numbers keep their structure and check digit. Names stay in their script.
  • Anything the layout does not cover is masked as free text. Deny by default.
  • A leak check fails the run if any original value survives, or if anything looks like a live card number. The report shows counts and locations, never values.

The leak check proves the classified values are gone. It cannot prove the classification is complete. A security sample review of the output is part of the procedure.

Pitfalls

Trusting declared lengths

Most fixed-length integration bugs start with a buffer sized from a total row. Compute lengths from the field list, compare with every declared figure, and refuse to generate anything until the difference has a recorded decision.

Letting core vocabulary into the contract

One abbreviation in a public schema becomes a dependency for every consumer. It survives any core change. The leak check is cheap; run it on every build, including descriptions and examples.

Putting rules in the adapter

A thin adapter becomes a fat one one “small rule” at a time. Then the bank has two places that decide eligibility. Composite operations may sequence steps and stop at the first failure. They may not decide anything the core decides.

Mistaking the simulator for the core

A green run against the simulator proves the integration and the contract. It does not prove the core’s business rules. Keep a short acceptance pass on the real core for each release, and feed every disagreement back into the catalogue or the simulator.

Steps to Adopt

  1. Compile the specifications into a catalogue

    Parse every message table into one JSON catalogue. Check every layout against its declared lengths. Record overrides and spec errors with their reasoning. Send the defect register to the core owner.

  2. Split codes into business domains

    Assign each code to a domain by code range, then title keywords. One domain becomes one API, one DFDL library and one adapter application — also a natural bulkhead.

  3. Write and review the design layer

    Operation per code, resource paths, audience, exclusions with reasons, vocabulary and flows. Review it per domain, with the consumers in the room.

  4. Build the generator with a leak check and a drift check

    Emit contracts, flows, internal mappings and DFDL models. Validate every contract. Fail on any core name in public output. Fail on any difference between committed and regenerated files.

  5. Fix the outcome model before the first consumer

    Declines as 2xx with status: FAILED. Problem details only for protocol failures. Idempotency keys on every command. Generate the result-code mapping from the documented codes.

  6. Build the simulator on the adapter’s runtime

    Same DFDL models, real wire format, encoding detected from bytes, generic reply construction, a stateful ledger, idempotency and fault rules. Sweep every code with a default request.

  7. Generate the contract tests and publish coverage

    Deterministic cases from contracts, mappings and seed. Parallel, serial and scenario phases. Schema mismatches as findings. A coverage matrix across every code, refreshed on every run.

  8. Feed real traffic back in, safely

    Mask production exports inside the bank, leak-check them, and turn them into seed data and replay cases. Every surprise becomes a catalogue fix or a new case.
