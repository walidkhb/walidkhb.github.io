The Live Code Is the Spec: Recovering Business Rules from a Legacy ESB Before You Rewrite It

Most rewrites of a legacy integration platform start with a document. A requirements pack, a design from the original project, a set of rulings someone senior made years ago. The new team builds to that document. Testing passes against that document. Then the new platform goes live, and the counterparties on the other end of the wire notice that something is different.

The document was never the specification. The specification is the code that runs in production today. It has been the specification since the day it went live, and every hotfix, every configuration change and every quietly commented-out line has amended it since. Nobody updated the document. Nobody had to. The system worked.

I recently led the rebuild of a regulated, externally facing integration service at a Saudi bank, replacing flows that had lived on a legacy enterprise service bus for years. This essay is about the method we used before writing the new platform, and about the decisions it pushed up to leadership. The method is not clever. It is just rarely done.

Why rewrites fail

Rewrites rarely fail because the new technology is wrong. They fail because the new system faithfully implements what everyone believes the old system does. The gap between belief and behaviour is invisible until cut-over, and by then it is a production incident with an external party watching.

The gap comes from three places. Source control does not always match what is deployed. Design documents describe intent, not the compromises made under deadline. And the people who made those compromises have often moved on. The result is a platform whose real rules exist in exactly one place: the running code.

If the old system and the new one disagree on the day of cut-over, the old one is not wrong. It is the baseline your counterparties have been reconciling against for years.

Archaeology before architecture

The first step was not design. It was an inventory. We catalogued the ESB estate: several hundred repositories across two generations of the platform, each classified by domain, technology and whether it still ran. Integration flows, API definitions, rules projects, scripts, configuration. Some repositories were dead. Some were alive but unowned. A few were the only surviving source for behaviour that mattered.

The inventory is unglamorous and it pays for itself many times over. It tells you where to dig. It tells you which flows touch the service you are replacing, including the ones nobody listed. And it surfaces the uncomfortable cases early: a rule engine whose deployed ruleset is not the one in source control, or a component whose source is simply missing.

Then we compared against what was actually deployed. Not the repository. The deployed artefacts and the exported rules from the production rule server. Where those differed from source control, the deployed version won. That single discipline changed more conclusions than any design workshop.

Numbered rules, not prose

From the live code we extracted every behaviour that a counterparty or an auditor could observe, and wrote each one down as a numbered business rule. One rule, one behaviour. Each rule pointed to the exact place in the legacy code where it lived. Each was grouped by service family and tagged with whether it had been verified against the deployed artefact or only against source.

Numbering matters more than it sounds. A numbered rule can be tested, cited in a decision, tracked in a gap matrix and closed. Prose cannot. Within weeks, the conversation shifted from “I think the old system does…” to “rule 41 says it does this, here is the line.” Arguments got shorter.

The catalogue then became the backbone of a gap matrix. For each rule: does the new platform match, partially match, differ, or not implement it yet? Or is the rule a defect that should not be carried forward? Parity became a number the steering committee could read every week, and the remaining gaps became a list with names on it.

Ruling against the live code

The hardest part was not extraction. It was confronting earlier decisions. Over the years, the business and architecture had made rulings about how the service should behave. Some of those rulings had never been implemented. Some had been implemented and later reversed in production. A few described behaviour that had never existed.

So we took every earlier ruling and set it next to what the live code does, with the rule numbers as evidence. For each, we wrote down the earlier ruling, the live behaviour, what the new platform did at that moment, and a recommendation. Then leadership ruled on each item, in writing.

The default policy was simple: follow live, unless the live behaviour is a defect or an earlier ruling encodes a legal obligation the bank must meet anyway. Live behaviour is what the counterparty receives today. Changing it during a platform migration means changing two things at once, and when results differ after cut-over, nobody can tell whether the migration or the change caused it.

That policy did not mean copying every flaw. Where live behaviour was clearly broken, we fixed it and recorded the fix as a deliberate, signed deviation. Where a legal obligation was missing, we built the capability and shipped it switched off by configuration, to be enabled after legal sign-off and after cut-over had settled. Parity first, improvement second, each with its own approval.

What drift looks like

Every legacy estate drifts in its own way, but the categories repeat. These are the kinds of things a rule-recovery exercise tends to surface. Expect to find each of them somewhere.

Deployed rules that differ from source control. A rules engine or a configuration store is updated directly in production, or a build is promoted from a branch that was never merged. The repository describes a system that no longer runs.

Fail-open on a dependency error. When a downstream check times out, the flow proceeds as if the check had passed. Sometimes this is a deliberate business choice. Sometimes it is an accident in an exception handler. The rewrite must know which, because a “cleaner” fail-closed design changes what counterparties see during every outage.

Retries that re-mint identifiers. A retry loop generates a new message or correlation identifier on each attempt. Anything downstream that correlates on that identifier silently loses track. The new platform should usually fix this, and the fix must be recorded as a deviation, because the counterparty will see different identifiers.

Logic disabled in production. A filter, validation or branch is commented out or switched off in every live build, while the documentation still describes it as active. The data the counterparty receives today reflects its absence.

Designed but never running. A path exists in the code, appears in the design, and cannot actually execute because of a defect nobody noticed, since the path is rarely triggered. Reproducing it faithfully means reproducing nothing.

None of these show up in a requirements workshop. All of them show up in production after cut-over if nobody looks first.

What leaders must decide

Rule recovery is engineering work. The decisions it forces are not. Four belong above the team.

The default policy. “Follow live unless defect or legal obligation” is a leadership statement. Without it, every engineer applies their own taste, and the new platform becomes a blend of the old system and a dozen private opinions about how it should have been.

Who signs a deviation. Every intentional difference from live behaviour changes what an external party receives. That needs an owner, a reason and, where relevant, the counterparty’s agreement. A deviation without a signature is just a regression with a good story.

Parity as the cut-over criterion. Go-live readiness should be measured against the rule catalogue, not against test cases written from the old document. If the gap matrix is not green, or every remaining gap is not covered by a signed ruling, the platform is not ready, however well it performs.

Funding the archaeology. The inventory and the rule extraction take weeks of senior time before a single line of the new platform is written. They look like delay. They are the cheapest insurance in the programme. The alternative is to discover the same rules one production incident at a time.

A rewrite is a promise that the bank will keep doing what it does today, on a better foundation. You cannot keep that promise without first finding out, precisely, what it does today. The live code is the only honest witness. Interview it first.
