Core Banking as a Product: Why the Core Should Stop Being Every Project’s Bottleneck

Ask any delivery lead in a bank what slows their project down. The answer is rarely the new channel, the new partner or the new cloud service. It is the core. Not because the core is slow. Because everyone has to queue for it.

At a Saudi bank, every project that touched customer accounts, payments or cards reached the core the same way: fixed-length messages over a queue, laid out byte by byte, described in long specification documents. Each team learned the format again. Each team met the same defects again. And each team waited for a slot on the one shared core test environment.

That is not an integration problem. It is a product problem. The core had no product — no contract, no catalogue, no test double. It only had an interface, and an interface is not the same thing.

How direct access turns the core into a bottleneck

Direct access feels cheap. There is no layer to build. A team reads the document, maps the fields and calls the core. The cost arrives later, and it arrives everywhere at once.

Knowledge concentrates. The layouts were documented, but not always correctly. When the team compiled every message table into a machine-readable catalogue, the arithmetic failed in 96 places. Signed amounts carried an extra byte no table mentioned. One heavily used reply was two bytes longer than declared. Every consuming team had found some of these the hard way, and patched them in its own code. The real specification lived in a few people’s heads.

Testing serialises. If the only way to test is against the real core, the core test environment becomes the critical path of the whole portfolio. Teams overwrite each other’s data. A missing test account stops a cycle for days. Negative cases — a blocked account, a timeout, a duplicate payment — are hard to set up and so are rarely tested at all.

Change becomes impossible. When dozens of consumers depend on the core’s field names, codes and byte offsets, the core cannot change without changing all of them. The bank has quietly signed a contract it never wrote down.

A core that every project must queue for is not a platform. It is a dependency with a waiting list.

What changed: a contract, a catalogue and a stand-in

The answer was to treat the core as a product with a published contract. Three things made that real.

A catalogue of everything. All 934 core transaction codes, every request and response layout, checked against the documents. Where a document was wrong, the correction was recorded with its reasoning and sent back to the core owner.

Fourteen governed business APIs, generated. One API per business domain — payments, accounts, cards, lending and so on — with about 1,280 operations in plain business English and standard formats. The contracts are generated from the catalogue plus a small, reviewed design layer. Nobody hand-writes them, and nobody hand-edits them. The public contracts name no core field and no core code. That mapping exists only in an internal design document. A thin adapter translates between the two and adds no business rules of its own.

A full core simulator. A stand-in that speaks the core’s real wire protocol for all 934 codes, with a small ledger behind it: holds, postings, reversals, duplicate detection, accounts in every awkward state, and injectable timeouts. On top of it, a test generator produced 6,256 contract test cases from the contracts and the test data, with a coverage matrix showing every code exercised.

The effect on delivery was immediate. Projects stopped queuing. Each team can run its own simulator, with its own data, at any hour. Negative and failure cases are now cheap to test, so they are tested. The shared core environment is kept for what only it can do: final acceptance on real business rules.

Replaceability is a by-product, not a programme

There is a second benefit that matters more over ten years than over one release. When consumers call business APIs that never mention the core’s internals, the core stops being a fixed point in the architecture.

That does not mean a bank should plan to replace its core. Most should not. It means the option exists. Upgrades, a split by product line, a new ledger for a new business — each becomes a change behind a contract rather than a change in every consumer. Options like that are cheap to keep and very expensive to buy back later.

The four designs on the table were honest about this. Letting consumers call the core directly gives no replaceability. A generic pass-through API that just wraps core field names in JSON gives none either — the contract is still the core. Building full domain services with their own logic gives replaceability but duplicates the bank’s most sensitive rules in a second place. Generated business APIs over a thin adapter give replaceability while the core keeps every rule. That was the trade worth making.

What leaders need to decide

The engineering is the easy part. A few decisions belong above it.

Is the core contract a product with an owner? Someone must own the catalogue, the design layer and the defect register — with authority to say no to a consumer that wants to bypass the APIs. Without an owner, the bank ends up with fourteen APIs plus the old direct access, which is worse than either.

What is a decline, and what is an error? The contract treats a bank decline — insufficient funds, a blocked account — as a successful call with a failed business outcome. Only transport problems are errors. That one rule changes how every dashboard, alert and retry policy behaves. It needs agreement from operations, not only from engineering.

Where must new consumers connect? The simplest control is architectural: new projects reach the core only through the business APIs. Existing consumers migrate domain by domain, as they change anyway. This is a governance decision, and it only works if it is enforced at the gateway rather than in a policy document.

Who closes the gaps with the core team? Building the catalogue and the simulator surfaced defects in the specifications and situations with no documented result code. Each one is a question only the core owner can answer. Leaders need to fund that conversation and track it to closure, or the contracts will carry open assumptions indefinitely.

What is the simulator allowed to replace? The simulator proves the integration and the contract. It does not prove the core’s business rules. Decide up front which tests run against the simulator, which run against the real core, and what evidence each release needs. Otherwise the simulator becomes either an unused toy or an over-trusted one.

None of these decisions is technical. All of them decide whether the investment pays back. When they are made, the core stops being the thing every project waits for. It becomes a product the whole bank builds on.
