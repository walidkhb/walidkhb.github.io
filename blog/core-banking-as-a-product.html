Core Banking as a Product: Why the Core Should Stop Being Every Project’s Bottleneck

Ask any delivery lead in a bank what slows their project down. The answer is rarely the new channel, the new partner or the new cloud service. It is the core. Not because the core is slow, but because everyone has to queue for it.

In many banks, every project that touches accounts, payments or cards reaches the core the same way: fixed-length messages over a queue, laid out byte by byte, described in long specification documents. Each team learns the format again. Each team meets the same defects again. And each team waits for a slot on a shared core test environment.

That is not an integration problem. It is a product problem. The core has an interface, but no product around it — no published contract, no machine-readable catalogue, no test double. An interface is not the same thing as a product.

How direct access turns the core into a bottleneck

Direct access feels cheap. There is no layer to build. A team reads the document, maps the fields and calls the core. The cost arrives later, and it arrives everywhere at once.

Knowledge concentrates. Interface documents for long-lived systems drift. Totals stop adding up, sign bytes go unmentioned, a reply turns out longer than declared. Each consuming team finds some of these the hard way and patches them in its own code, not always in the same way. The real specification ends up living in a few people’s heads.

Testing serialises. If the only way to test is against the real core, the core test environment becomes the critical path of the whole portfolio. Teams overwrite each other’s data. A missing test account stops a cycle for days. Negative cases — a blocked account, a timeout, a duplicate payment — are hard to set up, so they are rarely tested at all.

Change becomes expensive. When dozens of consumers depend on the core’s field names, codes and byte offsets, the core cannot change without changing all of them. The bank has quietly signed a contract it never wrote down.

A core that every project must queue for is not a platform. It is a dependency with a waiting list.

The operating-model shift: from interface to product

Treating the core as a product does not mean changing the core. It means changing what sits around it, and who owns that.

The message estate becomes data. Every request and response layout is held in a machine-readable catalogue, checked against its own arithmetic. Where a document is wrong, the correction is recorded with its reasoning and sent back to the core owner. Knowledge stops living in people and starts living in a reviewed artefact.

Consumers get business APIs, not message formats. One API per business domain — payments, accounts, cards, lending — in plain business language and standard formats. The contracts are generated from the catalogue and a small, reviewed set of design decisions, not hand-written. They name no core field and no core code. A thin adapter translates between the two and adds no business rules; the core keeps every rule it has today.

Teams test against a stand-in by default. A simulator that speaks the core’s real wire protocol, with a small ledger behind it, lets every team run its own core at any hour, with its own data. Holds, postings, reversals, duplicates, blocked accounts and timeouts become cheap to test, so they get tested. The shared core environment is kept for what only it can do: acceptance on real business rules.

The engineering for this is well understood. What changes is the operating model: the core team, the integration team and the delivery teams stop negotiating byte offsets project by project, and start working against one governed contract.

Business APIs and simulators are institutional assets

Most integration spend is project spend. A team builds what its project needs and moves on. The catalogue, the generated contracts and the simulator are different. They are built once and used by every project that follows, and each project makes them better — a new edge case becomes a new test, a surprise in production becomes a catalogue fix.

That changes how they should be funded and measured. They belong on the platform budget, not on the first project that happens to need them. Their value shows up in other teams’ plans: shorter test cycles, fewer environment conflicts, fewer late integration defects. A leader who measures them only by the project that paid for them will always find them too expensive.

Replaceability is a by-product, not a programme

There is a second benefit that matters more over ten years than over one release. When consumers call business APIs that never mention the core’s internals, the core stops being a fixed point in the architecture.

That is not a reason to plan a core change. It is an option. Upgrades, a split by product line, a new ledger for a new business — each becomes a change behind a contract rather than a change in every consumer. Options like that are cheap to keep and very expensive to buy back later.

The design choice decides whether the option exists. Letting consumers call the core directly gives none. A generic pass-through API that wraps core field names in JSON gives none either; the contract is still the core. Building full domain services with their own logic gives replaceability but duplicates the bank’s most sensitive rules in a second place. Generated business APIs over a thin adapter give replaceability while the core keeps every rule. For most banks, that is the trade worth making.

What leaders need to decide

The engineering is the easy part. A few decisions belong above it.

Is the core contract a product with an owner? Someone must own the catalogue, the design decisions and the defect register — with authority to say no to a consumer that wants to bypass the APIs. Without an owner, the bank ends up with business APIs plus the old direct access, which is worse than either.

What is a decline, and what is an error? A well-designed contract treats a business decline — insufficient funds, a blocked account — as a successful call with a failed business outcome. Only transport problems are errors. That one rule changes how every dashboard, alert and retry policy behaves. It needs agreement from operations, not only from engineering.

Where must new consumers connect? The simplest control is architectural: new projects reach the core only through the business APIs. Existing consumers migrate domain by domain, as they change anyway. This only works if it is enforced at the gateway rather than in a policy document.

Who closes the gaps with the core owner? Building a catalogue and a simulator always surfaces specification defects and situations with no documented outcome. Each one is a question only the core owner can answer. Leaders need to fund that conversation and track it to closure, or the contracts will carry open assumptions indefinitely.

What is the simulator allowed to replace? A simulator proves the integration and the contract. It does not prove the core’s business rules. Decide up front which tests run against the simulator, which run against the real core, and what evidence each release needs. Otherwise the simulator becomes either an unused toy or an over-trusted one.

None of these decisions is technical. All of them decide whether the investment pays back. When they are made, the core stops being the thing every project waits for. It becomes a product the whole bank builds on.
