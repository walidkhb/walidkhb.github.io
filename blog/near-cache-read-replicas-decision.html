Cache Architecture Is a Risk Architecture: Why Read-Replica and Near-Cache Decisions Belong at VP Level

Engineering teams frame caching decisions as performance optimisations. That framing is accurate for most of what they build — reducing latency, offloading database read pressure, keeping p99 response times below the SLA threshold. But in a financial-services context, the decision to route reads to a Redis replica or to serve values from a pod-local near-cache is not only a performance choice. It is a decision about how much staleness you are willing to tolerate in the data that drives customer-facing financial outcomes.

Replica lag is not a theoretical concern. During a SARIE settlement window, when write throughput to Redis spikes as settlement confirmations come in, replica lag on a loaded cluster can reach 100–500 milliseconds. If your settlement API is configured to read exchange rates from a replica with a 60-second near-cache TTL, that configuration was probably set up during a quiet afternoon in the development environment where replica lag was 2 ms. The 500 ms scenario was never tested. And the question of whether 500 ms of exchange rate staleness during a settlement window is acceptable is not a question that the engineer who configured the cache TTL is authorised to answer. It is a question for the head of operations and the VP of enterprise integration.

The classification table that every bank should own but most do not

The right governance tool for this problem is a data classification table: a document that lists every entity type that the caching layer stores, the maximum acceptable staleness for each type, who signed off on that staleness budget, and what the consequence of exceeding it is. This table does not live in the engineering wiki. It lives in the risk and control framework, referenced by the system design document, and reviewed annually or whenever a new entity type is added to the cache.

Building this table forces two conversations that are almost always deferred. The first is with the business owner of each data type: “If we serve an exchange rate that is 60 seconds old during a settlement, what is the financial and regulatory exposure?” For most exchange rates, the answer is acceptable because SARIE settlement uses a fixed daily rate and a 60-second lag during the settlement window is well within normal market movement. For payment authorisation state, the answer is never acceptable because a stale authorisation state can produce a duplicate payment, and SAMA’s real-time gross settlement framework does not forgive duplicate transactions.

The second conversation is with the technology risk and compliance function: “Which SAMA circulars and internal control policies constrain the staleness budget for each entity type?” The answer shapes the classification table in ways the engineering team cannot derive on their own.

The most dangerous caching configuration in a bank is not a cache that is too aggressive — it is a cache that was optimised correctly for one scenario and silently became incorrect when the data type or business context changed, without anyone re-examining the staleness budget.

What the leader needs to decide that cannot be delegated

Three decisions sit above the engineering level in a near-cache and read-replica deployment, because each one requires a view of business risk that the engineering team does not hold.

Which entity types are eligible for replica reads, and which must always go to the primary? Account balances and payment authorisation state must always read from the primary — zero replica lag, zero staleness. The engineering team knows this technically. But the classification of every other entity type — limit matrices, exchange rates, BIC routing tables, product configurations — requires a business owner to sign off on the staleness budget. That sign-off must be explicit and documented. Without it, engineers will make pragmatic choices based on performance profiles, and those choices will not reflect a considered view of regulatory exposure.

What is the acceptable behaviour during a Redis primary failover? When a Redis primary fails and a replica is being promoted, there is a 10–30 second window during which the cache state is uncertain. For reference data served from the near-cache, the near-cache TTL provides continuity. For entity types that require primary reads, the application should return a service-unavailable response rather than serve a potentially stale value from the now-promoted replica. The VP of enterprise integration needs to decide whether a 503 response on balance reads for up to 30 seconds during a Redis failover is acceptable, or whether a synchronous replica acknowledgement policy (WAIT 1 50) is required to reduce the failover-time data exposure. This is a business continuity decision, not a Lettuce configuration decision.

What is the near-cache invalidation SLA for limit changes? When the operations team modifies a customer’s transaction limit — a common action after a fraud alert or a risk review — the new limit must propagate to all pods’ near-caches before it takes effect for payments. The near-cache invalidation path (Redis keyspace notification → pod listener → Caffeine eviction) typically takes 5–30 milliseconds. But if a pod’s Redis subscription is interrupted (pod restart, brief network partition), the invalidation is missed and the pod serves the old limit for up to the near-cache TTL. The question of whether a 60-second window in which a pod might serve an old limit is acceptable is a risk decision. SAMA’s internal controls framework expects that limit changes are effective immediately in the transaction authorisation path. “Immediately” means different things to different stakeholders. The VP needs to define it before the engineers set the TTL.

What the team needs from leadership to get this right

The engineering team can implement the read-replica and near-cache topology correctly. What they cannot do without leadership is operate it safely over time. Three things need to be in place that are not engineering deliverables.

First, the data classification table needs to be a living document with a named owner and a review cadence. When a new entity type is added to the cache, there must be a process that requires a staleness budget sign-off before the entity goes to production. This process exists in well-governed banks; in most, it does not, and the classification table becomes stale within a quarter of its creation.

Second, the replica lag monitoring needs to be connected to an operational response. An alert that fires at 100 ms replica lag is only useful if someone is on call to respond, and if the response procedure specifies which read types to switch back to primary reads and which near-cache TTLs to reduce. Building the alert without the runbook is not a half-measure; it is false assurance.

Third, the near-cache configuration needs to be treated as a control, not a performance parameter. When an auditor from SAMA’s Technology Supervision Department asks how limit changes propagate to the transaction authorisation path and within what timeframe, the answer must be traceable to a documented configuration, a measured propagation SLA, and a signed-off staleness budget. “The engineer set the TTL to 30 seconds” is not a sufficient answer. The TTL must reflect a decision, not a default.
