Open Banking Conformance Is a Capability, Not a Certificate

Most Open Banking programmes are planned around a single moment: the day the conformance suite turns green and the certificate is issued. Budgets, vendor milestones and board updates all point at that date. It is a reasonable way to run a project. It is a poor way to think about an obligation that lasts as long as the bank offers the service.

A regulatory interface is not finished at go-live. The standard publishes errata. Profile versions tighten time windows and change audience rules. New API families arrive: account information first, then payments, then whatever the market adds next. Each change reopens the question the certificate answered once — does the bank still behave exactly as the standard requires? The institutions that answer it quickly are the ones that treat conformance as a capability they operate, not a certificate they hold.

Build or buy is the wrong first question

The debate usually starts with build versus buy for the authorisation server and the Open Banking APIs. Both routes are legitimate. A product brings speed and a ready-made security model. An in-house build brings control over the release cycle and deeper understanding of the standard. Banks succeed and fail on both paths.

The more useful first question is: who will be able to prove conformance after the next change, and how long will it take them? If the answer is “the vendor, at the next release, through a change request,” then the bank owns the obligation without owning the means to demonstrate it. If the answer is “our own pipeline, within a day,” the sourcing choice matters much less.

That reframing changes what to own. Even where the authorisation server is bought, the bank should own three things outright: the mapping from every profile rule to the control that enforces it, the automated conformance runs against its own environments, and the people who can read a new errata and say what changes. Those are the parts of the capability that no contract can transfer.

A certificate tells the regulator you were conformant on one day. A conformance capability tells them you can show it again on any day they ask.

Why automation matters after go-live

Conformance suites are mostly negative tests. They check that the server rejects an expired signed request, a token presented without its bound certificate, a consent that belongs to another provider. Those refusals are exactly what tends to break silently when an unrelated change lands: a library upgrade alters a default, a gateway rule is reordered, an error handler is refactored. Nothing fails in functional testing because the happy path still works.

Running the conformance suite only before a submission means those regressions are discovered months later, under deadline pressure. Running it automatically — a fast subset on every change, the full set nightly — turns conformance from an event into a build gate. The investment is modest: a scripted runner, generated configuration, a baseline of expected verdicts. The return is that the bank stays conformant between tests, not just on the day of them.

There is a second benefit leaders often miss. The same controls that FAPI 2.0 demands — signed requests, short-lived certificate-bound tokens, consent checked on every call — are the controls a bank wants for corporate APIs, partner integrations and internal high-value services. A team that can prove those controls continuously for Open Banking can extend the pattern to the rest of the API estate, on IBM, Red Hat or any other platform the bank runs.

How leaders should describe readiness

Open Banking status reports are prone to rounding up. “Passed conformance” can mean a sandbox run against a functional suite, a dry run against the OpenID Foundation plans, or a formal certification with a signed declaration. These are different statements with different consequences, and a regulator will read them back exactly as written.

A disciplined status report separates them:

Sandbox conformance. The implementation passes the functional suite in a test environment. It shows the controls work. It is not a licence to go live.

Strict conformance. The implementation passes the stricter, standard-level plans with every compatibility setting turned off. It shows that any accommodations made for test-tool behaviour are shims, not weaknesses.

Certification. The formal process, with evidence produced through the official route and a named person signing the declaration. Only this is “certified”.

Reporting the three separately costs a headline. It buys credibility with the regulator, with auditors and with the board, and it makes the remaining gap visible enough to fund.

The decisions leaders cannot delegate

Which profile version the bank commits to. Market standards and the international profiles built on them do not always agree on details such as how long a signed request may live. Engineering can make the value configurable. Leadership must decide which version the bank certifies against and own that position with the regulator.

How strict the bank is when test tools disagree with the text. Test tools are software and have quirks. The sound policy is strict by default, relaxed only in a named test configuration, logged on every use and blocked in production. That policy is a risk decision and needs a signature above the delivery team.

Where the trust boundary sits. Keeping the authorisation server and the resource APIs together simplifies security today; splitting them scales better but adds internal hops that the standard does not secure for you. Either is defensible. Leaders should know which trade they made and why.

Who owns the standard. Someone in the bank must be accountable for reading every errata, updating the rule-to-control map and confirming the automated runs still pass. Without that owner, conformance decays quietly until the next deadline exposes it.

What to take away

Start from the conformance suite, not the architecture diagram: it is the regulator’s definition of done, and most of it tests what the bank refuses. Automate it early and keep it running after go-live. Keep one map from every rule to the control that enforces it. Describe results precisely. And give a small, senior team the mandate to own the standard end to end, whatever the sourcing model.

Do that, and each new regulatory interface becomes a feature the platform can deliver on its own schedule, rather than a project that restarts from zero every time the standard moves.
